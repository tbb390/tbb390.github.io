深度学习：Batch、Batch Size、Epoch、Shuffle、Momentum

今天继续复习深度学习训练过程中的 Batch 和 Momentum，重点理解不同 Batch Size 对训练效率和训练效果的影响。

Batch、Epoch 与 Shuffle： 训练时将全量数据划分成多个 Batch，每次使用一个 Batch 计算 Loss 和梯度并更新参数。所有 Batch 都遍历一次就是一个 Epoch。通常每个 Epoch 开始前会重新 Shuffle 数据，再重新划分 Batch。

Batch Size 的区别： Full Batch 使用全部训练数据进行一次参数更新，梯度方向比较稳定，但是更新频率低；Batch Size=1 每次只使用一条数据，更新频率高，但梯度噪声较大，参数更新过程也更加不稳定。

GPU 与 Batch： GPU 具有较强的并行计算能力，在一定范围内增加 Batch Size 后，单个 Batch 的计算时间不会明显增加，因此大 Batch 通常能够更快完成一个 Epoch。

小 Batch 为什么有优势： 小 Batch 带来的梯度噪声并不完全是坏事。noisy update 可能帮助模型跳出鞍点和局部最优，并更容易找到泛化能力较好的平缓区域。因此 Batch Size 不能简单理解成越大越好，需要根据任务进行调整。

Momentum： 普通梯度下降主要根据当前梯度的反方向更新参数，而 Momentum 会结合之前的更新方向，让参数具有类似物理运动中的“惯性”。即使当前梯度接近 0，也可以依靠之前积累的移动方向继续向前。

Momentum 的直观理解： 可以把参数优化想象成一个从高处滚下来的小球。小球滚到鞍点或者局部极小值时，如果仍然具有足够的惯性，就可能继续向前运动，而不是直接停在当前位置。

今天重点： Batch Size 影响训练的计算效率、梯度噪声和泛化表现；Momentum 则是在梯度下降基础上加入历史更新方向，通过“惯性”帮助优化过程继续向前。

Agent开发：MinerU 复盘

【总】为什么用 MinerU？
因为 RAG 和企业知识库需要处理大量复杂文档，需要一个高精度、低成本、数据安全可控的文档解析工具，为后续大模型提供质量更高的中文语料。

1. Why / 为什么会用？
在 RAG 和企业知识库中，需要处理 PDF、财报、扫描件等复杂文档。云端 API 存在数据出境、合规和成本方面的问题；国外开源工具在中文场景下存在支持不足；如果直接使用超大模型进行解析，又会带来较高的算力和成本压力。

因此需要一个能够本地部署，同时能够较好处理中文复杂文档的解析工具。MinerU 的作用就是在 RAG 前面先完成文档解析和结构化处理。

2. What / MinerU 是什么？
MinerU 是一个开源的一站式文档解析工具，可以将 PDF、网页、图片等复杂内容转换成 Markdown、JSON 等结构化数据。

它涉及 OCR、版面分析、阅读顺序恢复、表格识别、公式识别等能力，可以将公式转换成 LaTeX、表格转换成 HTML，并支持多语言 OCR。其处理思路包括 Pipeline 和 VLM，其中材料中提到核心 VLM 模型约为 1.2B。

3. Before / 没用之前的问题：
普通 PDF 文本提取容易丢失文档结构。双栏排版可能出现阅读顺序错误，复杂表格可能出现结构断裂，扫描件还需要额外进行 OCR。对于中文文档，竖排文本、印章等内容也可能成为解析难点。

同时还需要考虑数据安全和成本。云端解析需要考虑企业数据上传问题，本地使用大型通用模型进行解析又会增加 GPU 和算力成本。

4. After / 使用之后：
使用 MinerU 后，可以对复杂文档中的文本、标题、表格、图片和公式等内容进行识别和整理，并输出 Markdown、JSON 等结构化结果。

通过 OCR、Layout Analysis 和 Reading Order 等能力，可以更好地处理复杂版面、文字识别和阅读顺序问题，同时保留表格、公式等结构，为后续 Chunk 和 Embedding 提供更合适的数据。

MinerU 也支持本地化运行，材料中提到其核心 VLM 模型约为 1.2B，因此相较于直接使用超大模型进行文档解析，可以降低对算力的依赖。

5. Result / 最终效果：
今天复盘材料中给出的数据包括中文 OCR 准确率 98.1%、公式识别 98%、表格识别 92%，OmniDocBench 得分 95.69，同时提到 GPU 成本节省约 60%。

对 RAG 来说，更重要的是解析结果能够以 Markdown、JSON 等结构化形式进入后续处理流程，从而减少因为文档结构丢失、阅读顺序错误等问题对 Chunk、Embedding 和 Retrieval 造成的影响。

【总】MinerU 在 RAG 中的位置：
MinerU 不是 RAG，也不是向量数据库，而是知识库构建前面的文档解析环节。

整体可以理解为： 原始文档 → MinerU → Markdown / JSON → Chunk → Embedding → 向量数据库 → Retrieval → Rerank → LLM。

所以 MinerU 不只是简单的“PDF 转 Markdown”，核心是尽可能保留复杂文档中的内容和结构，为后面的 RAG 提供更适合模型处理的知识输入。
