1. 项目整体介绍

Q：介绍一下你的Ragent项目？
Ragent是一个企业级 Agentic RAG 平台， 目标是让大模型结合企业私有知识完成更加准确的智能问答。 传统大模型存在：
1. 不知道企业内部私有数据。
2. 容易产生幻觉。 因此通过RAG方式，将企业知识作为外部上下文提供给LLM。 核心流程： 
文档上传
 ↓
文档解析
 ↓
Chunk切分
 ↓
Embedding向量化
 ↓
向量数据库存储
 ↓
检索
 ↓
Rerank
 ↓
Prompt构建
 ↓
LLM生成
技术栈： Java Spring Boot 3、 Redis、 PostgreSQL + pgvector、 RocketMQ、 Embedding模型、 MCP。
追问：为什么叫Agentic RAG？ 普通RAG： 用户问题 → 检索 → LLM回答。 Agentic RAG： LLM具备任务判断能力， 可以决定：
- 是否需要检索
- 是否调用工具
- 如何组合能力。

4. 上下文控制设计

Q：你的项目怎么设计上下文控制？
上下文控制主要解决两个问题：
1. Prompt长度限制
2. 无关历史信息干扰模型 我的设计主要包括：

① 检索内容控制 不是把整个知识库塞给LLM。 流程： 
Query

↓

Retriever召回TopK

↓

Rerank重新排序

↓

选择高相关Chunk

↓

进入Prompt
控制： - Chunk数量 - Token长度 - 相关性阈值 避免上下文过长。

② 历史对话控制 多轮对话不会无限保存。 会根据： - 最近对话窗口 - 用户问题相关性 选择需要保留的信息。
追问： 为什么不保存全部历史？ 回答： 因为LLM上下文窗口有限。 历史过长： 1. Token增加 2. 推理成本增加 3. 旧信息可能干扰当前任务。 所以采用窗口控制和摘要机制。

5. 多轮上下文存储设计

Q：多轮上下文你怎么设计？
设计分为短期记忆和长期记忆。 短期记忆： 保存当前会话上下文。 例如： 
conversationId

{

 user:"北京天气怎么样",

 assistant:"今天晴天"

}
存储： Redis。 特点： - 快速访问 - 生命周期短
长期记忆： 对于用户长期偏好或者重要信息， 可以进行： Embedding向量化。 保存到向量数据库。 下一次： 通过相似度检索召回。
追问： 为什么不用数据库保存全部聊天记录？ 回答： 关系数据库适合结构化查询。 但是历史对话中需要根据语义找到相关内容。 例如： 用户： “继续刚才那个方案。” 需要理解语义关联。 所以短期使用Redis， 语义记忆使用向量检索。

6. Embedding Pipeline性能优化

Q：你项目里面耗时优化怎么实现？
主要优化知识库构建阶段的Embedding流程。 原始流程： 

for(chunk){

调用Embedding API

等待返回

保存结果

}
问题： - 请求串行 - 网络等待时间浪费 - 吞吐较低 优化方案： Batch分片 + 4路有界并发 + 异常快速取消 + 结果保序合并

7. 为什么设计Batch分片？

Q：为什么不用单个Chunk调用Embedding？
单Chunk调用： 
chunk1

等待

chunk2

等待

chunk3

等待
大量时间消耗在网络等待。 Batch之后： 
[
chunk1,
chunk2,
chunk3,
...
chunkN
]

↓

一次Embedding请求
优势： 1. 减少API请求次数。 2. 提高模型计算利用率。 3. 提高整体吞吐。 但是Batch不能无限增大。 过大： - 请求超限制 - 内存增加 - 单次失败影响更多任务。 所以需要测试选择平衡点。

8. 为什么选择4路并发？

Q：为什么是4路？为什么不是8路或者16路？
4路并不是固定理论值， 而是根据实际测试得到的平衡点。 Embedding任务属于： IO等待 + 计算混合任务。 并发太低： 资源利用不足。 例如： 1路： 
请求

等待API

CPU空闲
并发太高： 会出现： - API限流 - 网络压力增加 - 内存占用提高 - 线程切换增加 因此设计： 

任务队列

↓

4个Worker线程

↓

Embedding
保证吞吐和稳定性的平衡。
追问： 你的4路并发怎么实现？ 回答： 通过线程池控制。 核心思想： 限制同时执行的Embedding任务数量。 例如： ExecutorService线程池： 核心线程数=4 最大线程数=4 超过任务进入等待队列。

9. 异常快速取消和结果保序

Q：如果其中一个Embedding任务失败怎么办？
如果Batch任务执行过程中： 某个任务失败。 不会继续等待所有任务。 流程： 

任务失败

↓

触发取消信号

↓

cancel其他Future任务

↓

释放资源

↓

返回异常
实现思想： 通过Future管理任务状态。 失败后： 调用： cancel(true) 取消未完成任务。
Q：为什么需要结果保序？
因为并发执行完成顺序是不确定的。 例如输入： 
chunk0
chunk1
chunk2
chunk3
完成： 
chunk2
chunk0
chunk3
chunk1
如果直接保存： 可能出现： chunk0文本对应chunk2向量。 这是错误的。 所以每个任务保存index： 
{
 index:0,
 text:"chunk0",
 vector:[]
}
最终按照index排序合并。

12. Recall@K怎么理解？

Q：Top5、Top20召回率是什么意思？
Recall@K表示： 正确答案是否出现在前K个召回结果中。 公式： 

Recall@K

=

命中的相关文档数量

/

全部相关文档数量
例如： 一个Query有： 3个正确Chunk： 

A

B

C
检索Top5： 

A

X

Y

Z

W
命中： 1个。 Recall@5： 

1/3

=33.3%
如果Top20： 包含： A、B、C。 Recall@20： 

3/3

=100%

13. 如果正确答案一个在Top5，一个在Top20怎么算？

Q：假如正确答案在Top5，另一个在Top20，这种怎么计算？
需要看评测指标定义。 如果计算Recall@5： 只看Top5。 例如： 相关Chunk： 

A

B
检索： Top5: 包含A Top20: 包含B 那么： Recall@5： 

1/2=50%
Recall@20： 

2/2=100%
所以： K越大， 召回覆盖率越高。 但是K越大： 进入Prompt的信息越多， 可能增加噪声。 所以实际系统需要平衡。

14. MRR指标是什么？

Q：除了Recall还看什么指标？
MRR： Mean Reciprocal Rank。 关注： 第一个正确答案出现的位置。 公式： 

MRR=

1 / 第一个相关结果排名
例如： 第一个正确答案： Top1： MRR=1 Top5： MRR=0.2 说明： 越靠前越好。 Recall关注： 有没有召回。 MRR关注： 排序质量。

15. 为什么采用混合检索？

Q：为什么不用纯向量检索？
因为企业知识场景中： 语义匹配和关键词匹配都有价值。 向量检索优势： 理解语义。 例如： “员工离职流程” 和： “人员退出手续” 可以匹配。 但是： 对于： 

订单编号

错误码

产品型号

法律条款编号
关键词检索更准确。 所以采用： 

向量检索

+

关键词检索

↓

结果融合

↓

Rerank
结合两者优势。

16. 向量数据库有什么价值？

Q：为什么需要向量数据库？普通数据库不行吗？
普通数据库： 例如MySQL。 主要适合： 结构化查询。 例如： 

select *

where id=100
但是RAG需要： 语义相似度搜索。 例如： 用户： “怎么申请退款？” 知识库： “售后退货流程” 关键词不同， 但是语义相关。 向量数据库存储： 

文本

↓

Embedding

↓

高维向量
然后通过： 余弦相似度、 向量距离 找到语义接近内容。
追问： 为什么项目使用pgvector？ 回答： 因为项目已有PostgreSQL基础设施。 pgvector可以： 1. 保存业务数据 2. 保存向量数据 3. 支持向量相似度搜索 降低系统复杂度。

22. 企业RAG的实际价值？

Q：RAG在企业里面有什么价值？
企业内部存在大量： - 文档 - 制度 - 产品资料 - 客服知识 传统方式： 人工搜索效率低。 RAG结合大模型后： 用户可以自然语言查询。 价值： ① 知识沉淀 将企业知识数字化。
② 降低人工成本 客服、内部问答自动化。
③ 提升信息获取效率 从关键词搜索升级为语义理解。
④ 保证回答可靠性 通过检索企业真实数据， 降低幻觉。
